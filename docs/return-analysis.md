# Return Module Analysis

## 1. Relationship between Return and Sale

The relationship between `Return` and `Sale` is an association.

A `Return` must reference an existing `Sale` because every return is created from a specific previous sale. However, a return is not a type of sale, so inheritance is not appropriate.

The `Return` class stores a reference to the original `Sale`, which allows the system to validate the return period, identify the customer, and verify that the returned products belong to that sale.

## 2. Representation of Partial Returns

Partial returns are represented using a `List<Product>` called `returnedProducts`.

This list contains only the products selected for the return instead of all the products from the original sale. This allows a customer to return one or more products from a sale without requiring the complete sale to be returned.

Before registering the return, `ReturnService` verifies that every selected product belongs to the original sale.

## 3. Thirty-Day Return Validation

The 30-day validation is part of the business logic and is therefore controlled by the service layer.

The `Sale` class provides the `canBeReturned()` method, which determines whether the sale is still within the allowed return period. `ReturnService` uses this method before registering a return.

The sale date is converted to `LocalDate`, and `ChronoUnit.DAYS.between()` is used to calculate the number of calendar days between the sale date and the current date.

A return is accepted when the number of days is between 0 and 30, inclusive.

## 4. Stock Restoration

The existing product stock management logic is reused through `ProductService`.

For the return module, the `restoreStock(String productId, int quantity)` method was added. This method follows the same persistence logic already used by the existing `updateStock()` operation: it loads the products, finds the corresponding product, modifies its stock, and saves the updated product list.

`ReturnService` invokes `restoreStock()` after all return validations have been completed.

Reusing the existing product service and persistence logic avoids duplicating inventory management code inside the return module and keeps stock operations centralized in the product service layer.

## 5. Monthly Balance

The monthly balance is generated by `ReturnService` because this operation requires information from both sales and returns.

`ReturnService` depends on `SaleService` to obtain the registered sales and on `ReturnDAO` to manage return information.

For the selected month and year, the service adds the totals of all sales registered during that period and separately adds the refund amounts of all returns registered during the same period.

The balance is calculated as:

`Monthly Balance = Sales Total - Returns Total`

Keeping this operation in the service layer preserves the layered architecture because the user interface only requests the calculation and does not directly access persistence or implement business rules.
